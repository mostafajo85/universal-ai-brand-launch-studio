## Blueprint and advanced interaction engine

Inspect the approved reference on desktop/mobile when supported: section sequence, hierarchy, scrolling, animation triggers/timing/easing, controls and responsiveness; capture screenshots where possible. Use original code and authorized media, not copied branding, proprietary code or unauthorized assets.

Design a product-specific narrative, information architecture, conversion journey, responsive layouts, approved copy and CTA. Select relevant sections (hero, features, product experience, showcase, commercial, use cases, FAQ, CTA). Propose one purposeful signature interaction, e.g. scroll-driven storytelling, product reveal, rotation, image sequence, parallax, micro-interactions, exploded view or WebGL/Three.js if appropriate. True 3D requires suitable actual assets and implementation; label simulations accurately. Balance ambition with speed, accessibility and mobile usability.

**Dedicated Scroll-Scrub Film:** when the approved reference and narrative benefit from a scroll-controlled cinematic experience, propose a purpose-built product film rather than automatically reusing a fast-cut commercial. Plan the scroll progression (0–100%), visual beats, product reveal, stable section boundaries, camera path, continuity, intended crop, text-safe regions and final frame. Prefer smooth, readable motion suitable for forward/backward seeking; avoid dependence on audio or rapid cuts. Verify the native scroll-scrub template or another supported implementation and its required media format. Compare existing approved footage against these requirements first; generate dedicated footage only if needed and approved. Include the proposed duration, model, references, resolution, compression, cost and mobile/reduced-motion fallback in the blueprint and asset plan. If using a film or image sequence, optimize seeking, loading and responsive cropping; use a poster/static alternative when motion is reduced or playback is unsupported. Test actual scroll-to-frame synchronization, direction changes, section boundaries, mobile behavior and performance. Never describe video scrubbing as true 3D interaction.

Select the actual technical stack based on the available website builder. If using Higgsfield's native builder, read its skill and references first; do not impose an incompatible framework. Use the supported scaffold and scroll-scrub template if available; check the live stack rather than imposing a framework. Ask whether a plain product website or an AI-integrated app is desired if ambiguous; default to a plain product website proposal for this workflow. Do not activate databases, AI features, billing, data collection or transactions without authorization.

**GATE 03B — Blueprint:** present reference analysis, section/layout plan, content, interaction specs, desktop/mobile approach, technical stack and asset strategy. Obtain approval before code or new assets.

## Assets and build

Inventory approved media, intended placement, missing assets, formats and dimensions. Use Higgsfield for necessary new media. Avoid unrelated stock and grey placeholders.

**GATE 03C — Assets:** show inventory and any new generation quote; obtain approval before generation. If new assets are produced, obtain their acceptance before integrating. If all existing assets are already approved for this use, simply confirm the build scope at this gate; no redundant asset-by-asset permission.

Build original maintainable responsive code with optimized media, reliable playback, keyboard controls, reduced-motion support, accessibility and sensible dependencies. For fictional products use a clearly nontransactional demo. For real products use only approved purchase links and commercial details.

For native website tools, follow the actual create/repository checkout/edit/commit/push sequence if exposed. Use a local/sandbox preview and supported browser testing before public deployment. A native deploy may immediately expose a public URL, with no separate private deployment stage: do not use it for unauthorized preview. If private preview is unavailable, present available source/screenshots and disclose limitations. Test at 1440×900 and 390×844: layout, navigation/CTA, interactions, playback, identity, accessibility, console errors and performance. Fix confirmed defects within scope; paid fixes require authorization.

**GATE 03D — Preview and deployment:** present actual preview or limitations, desktop/mobile evidence, QC, intended hosting and any cost. Obtain explicit approval for public deployment. Separately ask authorization for community feed publication only if relevant; never equate it with deployment.

Deploy using Higgsfield Supercomputer/native website deployment if available and approved. Verify returned status and actual live URL; test deployed desktop/mobile behavior. Do not report a pending build as live. Do not list it in the community feed or submit to contests without separate authorization. If deployment is unavailable, deliver working source when accessible and explain the limitation.

**GATE 03E — Website acceptance:** present live URL if verified, available source, previews, interactions and QC; obtain approval before Phase 04.
